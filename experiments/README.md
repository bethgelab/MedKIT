# MedKIT — Experiments

This subproject runs the knowledge-integration experiments reported in
the paper. It is a customized fork of the
[EasyEdit](https://github.com/zjunlp/EasyEdit) framework, extended for
sequential editing on time-stamped medical evidence updates and for
the three method families compared in the paper:

- **Knowledge editing**: AlphaEdit, MEMIT, WISE, GRACE, MEMOIR, IKE.
- **Continual post-training**: LoRA-Merge, O-LoRA, SEEKR.
- **Retrieval-augmented generation**: BM25-RAG, Dense-RAG.
- **Further baselines**: DPO, GRPO, Agentic-RAG — see
  [`further_baselines/README.md`](further_baselines/README.md).

Models evaluated in the paper are general-purpose LLMs (Gemma-3,
Qwen-3, LLaMA-3.1) and medical-adapted variants (MedGemma,
Bio-Medical-LLaMA-3) at 4B and 8B scales.

## Install

```bash
# Recommended: a fresh conda environment
conda create -n medkit python=3.10 -y
conda activate medkit

# Loose install (smaller surface, allows pip to resolve)
pip install -r requirements.txt

# OR: full pinned environment used for the paper experiments (with vLLM)
pip install -r pip-requirements.txt
```

Python 3.10 + CUDA 12.x are recommended. vLLM is optional but speeds
up generation-heavy probes (compositional, operational); see the
"vLLM" section below for caveats.

## Environment variables

| Variable               | Required        | Purpose                                                                                                          |
|------------------------|-----------------|------------------------------------------------------------------------------------------------------------------|
| `OPENROUTER_API_KEY`   | yes (LLM judge) | Routes the LLM judge that scores open-form responses (compositional, operational, locality probes).              |
| `WANDB_ENTITY`         | optional        | If set, runs log to W&B under this entity. Otherwise W&B is disabled (the default config has `entity: null`).    |
| `WANDB_PROJECT`        | optional        | Override the W&B project name (default `medkit-experiments`).                                                    |
| `TRANSFORMERS_CACHE`   | optional        | HuggingFace model cache. Defaults to `~/.cache/huggingface/transformers`.                                        |
| `HF_DATASETS_CACHE`    | optional        | HuggingFace datasets cache. Defaults to `~/.cache/huggingface/datasets`.                                         |

Note on `OPENAI_API_KEY`: not required for reproducing the paper.
`easyeditor/editors/utils.py:GPTWrapper` instantiates an OpenAI client,
but is only used when editing a model whose name contains `gpt`
(see `editors/editor.py:223`). None of the five paper-evaluated models
trigger this code path. If you extend the codebase to edit an
OpenAI-API-served model, set `OPENAI_API_KEY` then; otherwise leave
it unset.

Never hard-code API keys in the source. The included entry points
read them only via environment variables.

## Single experiment run

The entry point is `run_medkit.py`, a Hydra application:

```bash
python run_medkit.py --config-name=hemonc/main/weekly/memit_qwen3_4b
```

`--config-name` selects one YAML under `hydra/experiments/`. The
generator-emitted configs live under
`hydra/experiments/hemonc/main/{daily,weekly,monthly}/` (261 configs
spanning 11 methods × 5 models × 3 batching strategies, plus
auxiliary configs), together with 30 EVAL configs used by the DPO/GRPO
baselines in `further_baselines/`.

Outputs:

- **Metrics**: `metrics/main/hemonc/main/<strategy>/<config>/...*.json`
- **Checkpoints**: `checkpoints/main/hemonc/main/<strategy>/<config>/`
- **Logs**: `LOGS/main/<config>_<jobid>.out`

## Reproducing the paper's full sweep

The 261 main-experiment configs are auto-generated by
`main_experiments/generate_configs.py` from
`hparam_tuning/figures/best_params.csv`:

```bash
# Regenerate configs (idempotent — safe to re-run)
python main_experiments/generate_configs.py
```

Submission is via SLURM. A generic template is provided
as `main_experiments/slurm/main_edit_template.slurm`. Copy it and
fill in the `FIXME` placeholders for your cluster:

```bash
cp main_experiments/slurm/main_edit_template.slurm \
   main_experiments/slurm/main_edit_<your-cluster>.slurm
$EDITOR main_experiments/slurm/main_edit_<your-cluster>.slurm
```

The placeholders are: GPU partition name, GRES string, log path,
optional `--mail-user`, scratch cache directories, the absolute path
to your `experiments/` checkout, and the conda-init script path.

Then submit:

```bash
export SLURM_SCRIPT="$PWD/main_experiments/slurm/main_edit_<your-cluster>.slurm"

# Dry run — print what would be submitted
DRY_RUN=1 bash main_experiments/submit.sh --strategy weekly | head -20

# Real submission of all 87 weekly configs
bash main_experiments/submit.sh --strategy weekly

# Filter by method or model:
bash main_experiments/submit.sh --strategy weekly --method memit --model qwen3_4b

# Skip configs that already finished (resumable):
bash main_experiments/submit.sh --strategy weekly --skip-done
```

Monitoring:

```bash
# Live SLURM state plus checkpoint progress and log error parsing
python main_experiments/status.py --strategy weekly

# Just failures
python main_experiments/status.py --strategy weekly --status failed
```

Statuses: `complete`, `running`, `pending`, `stalled` (partial
progress, no job in queue), `failed` (most recent log shows an error),
`not_submitted`.

Resubmitting an already-running config picks up from the last saved
increment because every generated config has
`checkpoint.save: true` and `checkpoint.load: true` baked in.

## Walltime expectations

Approximate per-config walltime on a single H100, weekly batches
(48 update steps):

| Method family       | 4B model | 8B model |
|---------------------|---------:|---------:|
| Editing (MEMIT, AlphaEdit, GRACE, MEMOIR, WISE, IKE) |   2–6 h |   4–12 h |
| Continual (LoRA-Merge, O-LoRA, SEEKR)               |   3–8 h |   8–24 h |
| RAG (BM25, Dense)                                    |   1–3 h |   2–6 h |

Daily sweeps (~98 batches) take ~2× weekly; monthly (~14 batches)
take ~0.3×.

## vLLM

Generation-heavy probes (compositional, operational) use vLLM by
default for throughput. Three caveats:

1. **bio-medical-llama3-8b max context = 8192.** Configs cap
   `vllm_max_model_len: 8192` for this model. Some Dense-Abstract /
   BM25-Abstract prompts may still exceed this; the prompt builder
   left-truncates and prints a `[generate_fast_vllm]` warning.
   Expected behavior, not an error.
2. **GRACE / MEMOIR / WISE** override `eval_use_vllm=False` because
   their custom forwards don't replicate cleanly under vLLM. Don't
   override.
3. **vLLM v1 strict prompt-length validation.** If you see "decoder
   prompt longer than maximum model length" from any non
   bio-medical-llama config, it's a real bug.

## Hyperparameter tuning

The hparam search that produced
`hparam_tuning/figures/best_params.csv` is not re-run by this
release. You can adopt the published best hparams directly (the
generated configs in `hydra/experiments/hemonc/main/` already
inline-override per-method values from this CSV).

## Dataset

Every config sets `qa.data_path: 'hf://bethgelab/MedKIT'`: on first use the
benchmark is downloaded from the Hugging Face Hub and cached as CSV under
`experiments/data/medkit/` (override with `MEDKIT_DATA_DIR`). All entry points
(`run_medkit.py`, `further_baselines/`, `main_experiments/status.py`) resolve the
path through `medkit_data.py`.

To use a local copy instead, e.g. the CSV built by `data_construction/`, point
`qa.data_path` at it, either in the config or as an override:

```bash
python run_medkit.py --config-name=hemonc/main/weekly/memit_llama31_8b \
    ++qa.data_path=/path/to/medkit_v4_conflict_flagged.csv
```

The `further_baselines/` scripts take the same value via `--data_path`, and
`main_experiments/status.py` via the `MEDKIT_DATA_PATH` environment variable.
