# Further baselines — DPO / GRPO / Agentic-RAG

Additional baselines reported in the paper, alongside the knowledge-editing,
continual post-training and RAG methods of the main sweep:

- **DPO / GRPO**: text-only preference / RL fine-tuning with a LoRA adapter
  carried forward across increments (lifelong CL). Like every other method,
  they start from the base model: the first increment trains a freshly
  initialised LoRA adapter (see `lora_init.py` for the per-model LoRA settings).
- **Agentic-RAG**: an LLM query → retrieve → refine → retrieve → answer loop
  over a TF-IDF index rebuilt **per increment from that increment's own
  evidence** (self-retrieval; the corpus does not accumulate across increments).

**Why these live outside the editing pipeline.** DPO and GRPO are
*post-training* methods: they update the model with a full training loop and
their own data construction (preference pairs, reward functions), a different
mechanism from the knowledge-editing algorithms in `easyeditor/`. Agentic-RAG is
a *retrieval* method (no weight change). They keep their own training /
retrieval code here and are integrated only at the shared *evaluation* layer,
so their results are directly comparable with the main methods.

All three read the same benchmark CSV as the main sweep and use the same
`hemonc_batching.build_increments` increment contract (daily / weekly /
monthly).

## Layout

```
further_baselines/
  model_registry.py              # config_key ↔ model_folder ↔ HF id ↔ EVAL hparam stem
  lora_init.py                   # fresh-LoRA setup (rank, alpha, target modules per model)
  train_model_dpo_hemonc.py      # DPO trainer (TRL DPOTrainer + PEFT LoRA)
  train_model_grpo_hemonc.py     # GRPO trainer (TRL GRPOTrainer + label reward functions)
  run_agentic_search_hemonc.py   # standalone Agentic-RAG script; also a helper library
  eval_lifelong_adapters.py      # shared-eval driver for DPO/GRPO
  run_agentic_shared_eval.py     # shared-eval driver for Agentic-RAG
  requirements.txt               # extra deps for the DPO/GRPO trainers
  slurm/{dpo,grpo,agentic}_template.slurm
../hemonc_eval_protocol.py       # shared helpers (LLM judge, increment loading) for the scripts
../hydra/experiments/hparams/EVAL/<model>.yaml             # base-model hparams for EVAL runs
../hydra/experiments/hemonc/main/{strategy}/{dpo,grpo}_<model>.yaml
```

The DPO/GRPO experiment configs are generated by
`main_experiments/generate_configs.py` (`--method dpo`, then `--method grpo`).
Back up `main_experiments/manifest.csv` first: the generator rewrites it with
only the selected method.

## Evaluation

Both drivers score through the main harness (`compute_edit_quality`: generation
+ LLM judge), so every number is comparable with the main methods and uses the
same per-increment result schema:

```
metrics/main/hemonc/main/{strategy}/{dpo,grpo,agentic_rag}_{model}/EVAL/data_-1_42/
    {increment}_mix_noevidence_base_gpt-4o-mini-hemonc_results.json
```

This is the evaluation used for the paper. The trainers and
`run_agentic_search_hemonc.py` additionally write their own *standalone*
self-evaluation (constrained label log-prob accuracy + judge) to
`<result_root>/{model_folder}/{strategy}/`. It scores closed questions
differently and is kept only as a sanity check; it is not what the paper
reports.

## Prerequisites

- **`OPENROUTER_API_KEY`** exported for the LLM judge.
- **Environment.** Agentic-RAG runs in the main experiments environment. DPO/GRPO
  need TRL; install `further_baselines/requirements.txt` into a separate
  environment (TRL's trainers need a newer PEFT than the pinned editing stack).
  Run everything from `experiments/` with it on `PYTHONPATH` (the SLURM
  templates set this; the scripts also add it themselves).

## How to run

DPO / GRPO: train per-increment adapters, then score each increment through the
EVAL harness (increment *i* is scored with the adapter trained *through*
increment *i*; an increment without training data reuses the previous adapter):

```bash
sbatch --export=ALL,BATCHING_STRATEGY=weekly further_baselines/slurm/dpo_<your-cluster>.slurm   # array 0-4 = the 5 models
sbatch --export=ALL,BATCHING_STRATEGY=weekly further_baselines/slurm/grpo_<your-cluster>.slurm
```

Agentic-RAG:

```bash
sbatch --export=ALL,BATCHING_STRATEGY=weekly further_baselines/slurm/agentic_<your-cluster>.slurm
```

Or drive a single (model × strategy) directly from `experiments/`:

```bash
python further_baselines/eval_lifelong_adapters.py \
  --combo dpo --config_key medgemma_4b --strategy weekly \
  --adapter_root /path/to/dpo/adapters --skip_existing
python further_baselines/run_agentic_shared_eval.py \
  --config_key medgemma_4b --strategy weekly
```

Both drivers accept `--n_increments N` for smoke tests and `--dry_run` to print
what they would do.

### Agentic-RAG variants

`run_agentic_shared_eval.py` exposes three axes; the defaults reproduce the
paper setting:

| Flag | Default | Alternative |
|---|---|---|
| `--retriever` | `tfidf` | `dense` (PubMedBERT embeddings via the DenseRAG retriever) |
| `--corpus` | `self` (per-increment evidence only) | `accumulating` (seeded with pre-increment evidence, as for BM25/Dense RAG) |
| `--backend` | `hf` (local model) | `openrouter` (API model from `hparams/EVAL/<--openrouter_stem>.yaml`) |

Use `--combo_name` to write a variant to its own output directory.

## Implementation notes

- The DPO/GRPO driver injects the trained adapter via
  `++hparams.adapter_path=<dir>` and passes `++adapter_path=null` so the
  top-level flag stays unset; otherwise the results-filename tag flips from
  `_base_` to `_finetuned_`. It also passes
  `++qa.batching.increment_filter=<label>` (handled in `run_medkit.py`) to
  score one increment per invocation.
- `OracleRAGHyperParams` (used by `editing_method=EVAL`) has an `adapter_path`
  field so the injected override survives `from_hparams()`'s field filter.
